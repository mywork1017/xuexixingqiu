# 点位数据维护规范

本规范适用于上海学习地图中图书馆、食堂、自然点位的发现、采集、准入、定位、去重、字段编辑、图片处理、SQLite 入库、云端推送和纠错。后续所有批量任务与单点维护均按本规范执行。

## 1. 数据权威与基本原则

- 管理后台 SQLite `admin/prisma/dev.db` 是点位唯一主库，Prisma 模型位于 `admin/prisma/schema.prisma`。
- 微信云数据库 `places` 是发布镜像；发布时按指纹增量写入变化或云端缺失的地点，并清理主库已删除的云端记录；云端数据不能反向覆盖主库。
- CSV 只作离线备份，禁止参与导入、生成或回写。
- 管理后台网站只查阅、调整现有字段和照片。新增、批量修改、合并和删除由 Codex 维护主库。
- 研究材料统一放在 `data/research/`，批量写入前的数据库备份统一放在 `data/backups/`。
- 自动采集、分类、评分和去重只产生候选或审核报告。涉及点位身份、准入、坐标、人物、水印和最终文案的决定必须由 Codex 结合完整证据终审。
- 信息不足时保留空字段或待审核记录，禁止用猜测、相似地点或旧资料补齐。
- 文档规则与代码校验出现差异时暂停写入，在同一轮维护中修正规则或实现并重新测试。

### 新城市任务的交付目标

- 用户要求制作一个新城市的数据时，默认交付范围包含：城市准入规则、完整点位清单、名称、地址、GCJ-02 坐标、营业时间、简介、合格图片、SQLite 入库、全量质量检查和增量推送。不能把搜索结果、低清缩略图、未经终审的批量候选当作成品。
- 开工前完整阅读本规范，检查当前主库、已有城市实现、采集脚本、审核脚本和推送方式。沿用本规范的 Crawl4AI 多渠道采集方案，不因单一渠道抓取方便而降低证据与图片标准。
- 先在内部完成代表性样板校准：至少覆盖城市总馆或旗舰馆、普通分馆、社区小馆、食堂各 1 个；没有对应类型时跳过。样板通过名称、地址、时间、简介和图片终审后再批量处理，无需等待用户逐项指出明显质量问题。
- 每个点位都必须主动扩大搜索范围，直到获得能清楚识别场所类别与具体地点的合格首图。若最终只有门口石碑、局部标识、低清门头或缺乏场馆主体的图片，视为采集未完成，继续检索官方媒体、建筑机构、新闻、地图平台、大众点评、小红书、携程等渠道；网上素材确实不存在时记录完整检索过程和缺口，不能降低首图门槛。
- 完成标准以用户在小程序中能直接理解地点为准：看到首图能判断场所类别并尽量识别具体场馆；打开详情能获得可靠地址、时间、简介和多角度环境信息。

## 2. 数据模型与字段规则

主库核心字段如下：

| 字段 | 规则 |
| --- | --- |
| `id` | 点位稳定标识；更新、纠错和同步时保持不变，确认重复并合并时才处理旧 ID |
| `name` | 使用当前官方全名，保留能区分总馆、分馆、街道、镇、社区和服务对象的限定词 |
| `category` | 仅允许 `图书馆`、`食堂`、`自然` |
| `address` | 使用公开可导航的完整地址，至少含城市、区县和道路门牌；园区、村宅等场景补充楼栋、楼层、入口或结构化定位信息 |
| `latitude`、`longitude` | 数值型 GCJ-02 坐标，落在支持城市范围内并与地址、入口或建筑相符 |
| `hours` | 使用可回查来源中的明确时段，至少含一个 `HH:MM`；无法确认时留空，禁止写“以现场公示为准”充当有效时间 |
| `description` | 只写当前点位可验证的实用信息，遵守第 9 节 |
| `photos` | `PlacePhoto` 关联记录，按 `sortOrder` 排序；自然类最多 10 张，其他分类最多 5 张，遵守第 10 节 |
| `updatedAt` | Prisma 自动维护，发布时转为日期字符串 |
| `pushedFingerprint` | 内部发布状态；字段或照片变化后应失效，成功推送后重新生成 |

每次字段变更都要能追溯到来源或明确的纠错证据。禁止在用户界面展示来源渠道、抓取过程、审核策略和内部数据规则。

## 3. 点位准入与排除

### 图书馆

- 收录面向公众开放、名称或官方资料明确确认属于图书馆体系的场馆。
- 区级馆、街道馆、镇级馆、总馆、分馆和少儿馆分别作为独立点位时，必须有独立馆址或明确的官方机构层级。
- 排除学校、大学、学院、幼儿园及校区内部图书馆。
- 排除机关、单位、公司、集团、银行、医院、军队、协会、商会、工会和企业内部场所。
- 排除城市书房、书房、图书室、阅读空间、借阅点和流动图书服务；名称明确包含“图书馆”且官方资料确认公开服务时可进入人工复核。
- 党群、党建、文化中心和社区中心内的空间，名称或官方资料必须明确包含并确认“图书馆”；仅有阅读角、自习区或文化空间描述时不收录。

### 食堂

- 只收录社区食堂、长者食堂、老年助餐点、市民食堂、邻里食堂及公益助餐场所。
- 必须有面向社区居民、老年人或公众提供餐食服务的证据。
- 排除学校、单位、机关、公司和封闭园区内部食堂。
- 排除普通商业餐厅、自助餐厅，以及名称仅含“自选大食堂”“自助大食堂”且无公共助餐属性的场所。

### 自然

- 收录公众可进入的城市公园、社区公园、口袋公园、公共绿地、游园、郊野公园、森林公园、湿地公园、可攀登山林、湖岸、岛洲、沙滩、滨江滨河湖滨公共空间、绿道和风光带；来源范围覆盖公开地图 POI、文旅与景区资料及其他可核实公开渠道，不限于政府公园名录。
- 名称未含类型词时，须有政府名录、管理单位或可核验地图 POI 证明它是独立公开自然空间。
- 风景区、自然保护地和植物园可收录；封闭施工、长期不对外开放的区域留作候选。
- 排除住宅小区内部绿化、学校或单位内部绿地、私家花园、高尔夫球场、道路中央隔离带和无独立游访空间的普通行道绿化。

### 城市范围

- 当前支持上海、苏州、嘉兴、南通、无锡、镇江。新增城市前需补充行政区列表、坐标边界、地图核验方式和对应测试。
- 上海坐标粗检范围：纬度 `30.6–31.9`，经度 `120.8–122.2`。
- 苏州坐标粗检范围：纬度 `30.7–32.1`，经度 `119.8–121.3`。
- 嘉兴坐标粗检范围：纬度 `30.25–31.05`，经度 `120.3–121.35`。
- 南通坐标粗检范围：纬度 `31.55–32.75`，经度 `120.2–122.05`。
- 无锡坐标粗检范围：纬度 `31.05–32.1`，经度 `119.45–120.75`。
- 镇江坐标粗检范围：纬度 `31.55–32.4`，经度 `118.9–119.95`。
- 边界范围只用于拦截明显错误坐标，不能证明点位身份或精确落点。

## 4. 点位来源与证据门槛

### 新增点位最低证据

- 至少 1 个来源证明场所名称、类别和公共服务资格。
- 至少 1 个独立地图或地址来源证明完整地址和坐标。
- 同名、多分馆、搬迁、改名或易混淆点位至少使用 2 个独立强来源交叉核对。
- 每个点位的信息补充目标覆盖至少 3 类独立渠道；渠道不足时记录缺口，未经核实字段留空。
- 同一篇内容的转载、聚合页和搜索快照按同一来源计算。

### 来源强度

1. 场馆官网、运营单位官网、政府门户、政务公开、文旅局、教育局、民政部门、街道或镇政府、公共图书馆服务平台、公开服务名录。
2. 场馆或运营单位官方公众号、政府政务号、官方新闻稿、官方活动回顾、官方视频号文章页。
3. 新华社、解放日报、上观新闻、文汇报、上海发布、苏州发布及区县融媒体等署名清晰、时间明确的新闻来源。
4. 建筑设计机构、室内设计媒体、行业协会、学校或社区公开页面，用于补充空间和设施信息。
5. 腾讯地图、高德地图、百度地图、Apple 地图中国区等公开 POI，用于地址、别名、入口和坐标核验。
6. 大众点评、小红书、微博、携程、马蜂窝等公开内容，是补充近期内部环境、座位区域和设施图片的重点渠道；应主动扩大检索覆盖，仍不能单独证明点位身份。
7. 百度、搜狗、必应、360、微信搜索和图片搜索只作来源发现入口，搜索结果摘要与缩略图不能直接入库。

### 时效与冲突

- 名称、地址、开放状态和营业时间优先使用最新官方信息。
- 设施和内部环境优先使用近期资料，并与当前馆址、装修或搬迁时间核对。
- 来源冲突时记录双方 URL、日期和冲突字段，优先采用更新、层级更准确的官方来源；仍无法确认时暂停该字段。
- 页面失效时保留已有归档、抓取时间和内容摘要，同时寻找新的可访问来源进行复核。

## 5. Crawl4AI 采集规范

- 网页搜索结果、来源页、正文、图片候选和设施证据统一优先使用 Crawl4AI 采集。
- Crawl4AI 需开启 JavaScript 渲染和懒加载等待；按页面结构提取正文、链接、图片原地址、`srcset`、背景图、图注、相邻文字、页面元数据和结构化数据。
- 批量任务使用限速、并发控制、缓存和失败重试；需要确认最新页面时使用刷新或 `CacheMode.BYPASS`，并记录抓取时间。
- 搜索阶段只产生候选 URL；来源阶段必须回到原始页面再次抓取。搜索摘要、重定向页和缩略图不能充当最终证据。
- 图片补充任务应主动抓取小红书和大众点评公开页面，查询词组合地点正式全名、分馆名、完整地址及“内景”“座位”“阅读区”“自习区”“用餐区”“设施”等词；同一地点尽量覆盖多个独立帖子和不同发布时间。
- 小红书、大众点评页面先由 Crawl4AI 抓取帖子标题、正文、地点标签、发布时间、图片原地址和图片上下文；页面交互导致内容无法完整提取时，可用 `xhs-cli` 或 Playwright 辅助读取，结果仍需回存到统一证据档案。
- Crawl4AI 归档至少保存：任务版本、点位 ID、点位全名、分类、查询词、渠道、原始 URL、最终 URL、页面标题、发布时间、抓取时间、地址上下文、正文或 Markdown、图片 URL、图片说明、内容哈希、成功状态和错误信息。
- 每项字段结论在审核文件中列出具体证据文件或 URL，保持“结论—来源—抓取内容”可追溯。
- Playwright 仅用于地图画布、必须交互才能出现的公开 POI 和 Crawl4AI 无法提取的动态页面；普通网页正文与图片来源仍应先尝试 Crawl4AI。
- 只采集公开可访问页面，遵守站点访问要求；不绕过登录、验证码、付费墙或访问控制。

现有 Crawl4AI 工具：

| 工具 | 用途 |
| --- | --- |
| `scripts/crawl-place-enrichment.py` | 按百度、搜狗、微信及平台渠道归档多渠道搜索结果 |
| `scripts/crawl-place-enrichment-sources.py` | 解析搜索结果并完整归档来源页，筛选地址、时间、设施和图片证据 |
| `scripts/crawl-place-facility-evidence.py` | 搜索 Wi-Fi、插座、饮水、卫生间、楼层、电梯、无障碍、停车等设施线索 |
| `scripts/crawl-place-facility-sources.py` | 解析并归档设施来源页 |
| `scripts/crawl-place-photo-sources.py` | 从百度、必应、搜狗、360 图片搜索发现图片来源 |
| `scripts/crawl-suzhou-place-sources.py` | 抓取苏州官方图书馆和公共助餐来源并生成候选 |

## 6. 名称与地址校验

### 名称

- 使用来源中最新、层级最完整的正式名称。
- 总馆、分馆、少儿馆、街道、镇、社区和服务对象限定词不得随意省略。
- 地图简称可记录为检索别名，不能覆盖有明确依据的正式名称。
- 改名时核对旧名、新名、地址和公告日期；确认同一机构后更新原记录，避免新增重复点位。

### 地址

- 城市地址优先写到“城市 + 区县 + 道路 + 门牌号”，保留弄号、楼栋、楼层和入口等导航必需信息。
- 农村点位可使用自然村、组、宅号等完整结构；园区、小区、邻里中心和大型建筑需补充门、楼、层或相对位置。
- 道路别名中的“路”“公路”“大道”可在校验时归一化，主库保留当前官方写法。
- 门牌范围可覆盖单个门牌，例如 `1702–1708号` 可支持 `1708号`；同路不同门牌必须判为不匹配。
- 两边都提供弄号时必须核对弄号；区县冲突、道路冲突或门牌冲突直接进入人工复核。

## 7. 定位、坐标与地图校验

### 坐标标准

- 小程序地图与导航使用 GCJ-02。WGS84 地理编码结果写入前必须转换为 GCJ-02。
- 坐标应落在场馆建筑、公共入口或可导航入口附近，禁止使用行政区中心、道路中心、搜索视口中心或邻近同名 POI。
- 地址修改后必须重新定位；名称或简介修改且地址未变时可保留已核实坐标。

### 定位工具顺序

1. 以官方完整地址作为查询输入。
2. 后台上海地址定位先查询 Nominatim；返回 WGS84 后转换为 GCJ-02。
3. Nominatim 无有效结果时使用 ArcGIS Geocoding，候选分数至少 90，类型限 `PointAddress`、`Subaddress`、`StreetAddress`，再转换为 GCJ-02。
4. 使用 Apple 地图中国区（高德底图）、腾讯地图、高德地图或百度地图复核 POI 名称、道路门牌和入口位置。
5. 苏州批量候选可用 `scripts/geocode-suzhou-place-candidates.py` 通过 Apple 地图中国区核验。
6. 地图页面需要交互时使用 Playwright/Chrome；网页类地址证据继续使用 Crawl4AI 归档。

### 候选接受规则

- 区县、道路和门牌号必须一致；标准化后的完整地址相同也可接受。
- 当前评分基线：区县匹配 15 分、道路门牌匹配 60 分、名称相关 25 分；自动接受要求区县与道路门牌匹配且总分至少 75。
- 名称相同不能抵消错误门牌。地址只到道路、行政区或商圈时，坐标保持待核验状态。
- 名称候选需要核对正式名称、分馆层级和服务类型；同名点位优先按地址定位。
- 自动位置修正中，移动不足 10 米通常不写入；移动 10–500 米需保留地图证据；移动超过 500 米必须人工复核。官方搬迁、旧坐标明显错误等情况可人工确认后超限修正。
- 写入后检查地图 marker、详情页地图和微信导航终点，确认落点没有偏到邻楼、道路对侧或同址其他机构。

### 相关工具

- `admin/lib/geocode-address.ts`：Nominatim、ArcGIS 和 WGS84→GCJ-02 转换。
- `scripts/geocode-suzhou-place-candidates.py`：苏州候选 Apple 地图核验。
- `admin/scripts/audit-all-map-pois.mjs`：全量 Apple 地图中国区 POI 审计。
- `admin/scripts/apply-map-position-audit.mjs`：按阈值生成或应用坐标修正，应用前备份。
- `scripts/prepare-official-songjiang-canteens.mjs`：腾讯地图定位的专项数据准备脚本。

## 8. 重复点位与合并

- 先按“分类 + 标准化名称 + 标准化地址”检查完全重复。
- 同类点位 60 米内全部进入近距离重复审计，重点检查同地址、同道路门牌和名称相关性。
- 同名图书馆 250 米内、同名食堂 80 米内应追加复核；名称高度相似且距离接近时也需复核。
- 同址的总馆、少儿馆、分馆或不同服务机构可以保留独立记录，前提是官方机构层级、入口或服务对象明确不同，并记录人工复核原因。
- 只凭坐标接近不能合并。合并前核对名称、类别、门牌、机构层级、营业时间、图片和来源。
- 批量合并先运行 `npm --prefix admin run dedupe:places` 预演；确认报告后才可运行 `npm --prefix admin run dedupe:places -- --apply`，应用前必须生成 SQLite 备份。
- 合并时选择证据最完整的记录作为主记录，保留准确地址、坐标、时间、简介和通过审核的非重复图片；云端旧 ID 在下次增量同步时清理。

相关工具：`admin/scripts/audit-nearby-place-duplicates.mjs`、`admin/scripts/dedupe-place-data.mjs`、`scripts/lib/place-data-quality.mjs`。

## 9. 营业时间与简介

### 营业时间

- 采用当前馆址、当前服务点的最新官方时段，至少包含一个明确的 `HH:MM`。
- 区分工作日、周末、闭馆日、午晚餐和法定节假日安排；长期规则与临时通知分开判断。
- 电话号码、地址、票价和“现场公示”不能混入营业时间字段。
- 只有旧资料、冲突资料或临时活动时间时留空，并在研究记录中标注原因。

### 简介事实

- 简介只写能由当前准确地点来源验证的实用事实，来源需要匹配全名、分馆和地址。
- 图片只能证明画面中清楚可见的内容。座位数、插座、Wi-Fi、饮水、停车、无障碍和餐饮服务等信息需要文字来源或清楚可核实的现场证据。
- 图书馆优先写楼层或入口、座位与阅读区、书架或儿童区、插座、Wi-Fi、饮水、卫生间、电梯、无障碍和停车。
- 食堂优先写座位与用餐区域、档口或菜品类型、点餐和支付方式、开放对象、取餐动线、饮水、卫生间与无障碍。
- 自然类优先写入口方位、沿水或环园步道、草坪和林下空间、亲水平台、儿童活动区、运动场地、座椅、公厕、无障碍、停车、门票和开放范围；简介可比其他分类更完整，仍只保留可回查事实。
- 已核实的限制信息可以保留，例如插座少、无 Wi-Fi、座位紧张或只对特定人群开放。

### 简介写法

- 使用一个紧凑段落，按信息价值排序，只保留具体事实。
- 禁止宣传口号、主观夸赞、榜单式结论、无证据推荐和“网红打卡”“氛围感很好”等空泛表达。
- 禁止“适合学习”“适合阅读”“想读书”“想自习”等泛化场景词；“自习区”“自修室”“阅读区”等具体空间名称可以使用。
- 禁止重复完整地点名，禁止出现小红书、大众点评、百度、高德、腾讯地图、微博、Google 等来源名称。
- 禁止把抓取、审核和数据规则写进面向用户的简介。
- 首尾不留空格，结尾不加句号、逗号、分号、感叹号或问号。

相关工具：`scripts/crawl-place-facility-evidence.py`、`scripts/crawl-place-facility-sources.py`、`scripts/compact-place-facility-evidence.py`、`scripts/apply-curated-facility-descriptions.py`、`tests/place-data-quality.test.js`。

## 10. 图片采集与审核

### 数量与内容

- 自然类每个地点最多 10 张，其他分类最多 5 张；图书馆与食堂的大楼或场馆外观最多 1 张。
- 自然类图片优先覆盖能识别具体地点的入口或全景、沿水视野、植被与步道、草坪或林下空间、主要活动设施；首图需显示整体景观或有地点身份的标志性景观。
- 图书馆与食堂以 2–5 张合格图片为目标，自然类以 4–10 张为目标；公开素材确实稀缺的小型社区点位可保留 1 张。数量目标不能用重复、低清或身份不明图片补足，数量差异不能改变单张图片和首图的质量门槛。
- 图片组首图承担地点识别：图书馆优先使用带清晰馆名的完整建筑、入口或具有唯一性的标志性馆内空间；食堂优先使用带清晰店名的入口、完整用餐区或可确认运营主体的场景。
- 每个点位的首图必须呈现完整、清楚且可识别的场所主体。图书馆首图应包含清晰馆名的建筑或入口，或使用来源充分、具有唯一识别度的标志性主空间；食堂首图应包含清晰名称的入口、完整用餐空间或可确认运营主体的代表性场景。只拍石碑、路牌、局部门头、墙角、储物柜、饮水机、空走廊、桌椅局部和普通书架的图片不能作为任何点位的首图。
- 后续图片优先内部座位、阅读或用餐区域、书架、服务台、儿童区、特色空间、充电、电梯、饮水和无障碍设施等能说明真实使用体验的画面。
- 同一区域、同一机位、近似构图和轻微角度差异的图片只保留质量最好的一张；每张图片都应增加新的场景或设施信息。
- 图片不足时允许低于分类目标，禁止用相似地点、同名地点、其他分馆或邻近场馆补足。

### 可识别性与技术质量

- 单张图片需同时通过四项硬门槛：准确属于当前点位、主体清楚、画面有信息价值、处理后可正常展示。任一项不通过即淘汰。
- “画面里有书”只能证明场景类似图书馆，不能证明属于当前分馆。普通书架、桌椅和走廊只有在来源页明确对应当前馆址，且图片组已有可识别首图时，才能作为补充图。
- 优先获取原图、`srcset` 最大图或平台可访问的最高分辨率版本，禁止使用搜索缩略图、截图、预览缓存图和反复压缩图。原图短边以不低于 960 像素为优先目标；唯一且清晰的官方身份图可低至 640 像素，需在审核记录中说明，禁止把放大后的尺寸当作原图质量。
- 排除明显虚焦、严重噪点、过曝欠曝、畸变、主体过小、遮挡严重、拼贴边框过多、手机界面截图、海报和宣传图。官方图片也必须经过同样审核。
- 方图裁切后馆名、门头、建筑主体、书架或用餐区不能被截断。原图合格但方图失去身份信息时，应调整裁切锚点或更换图片。

### 身份核验

- 审核细到准确馆址和分馆层级，完整区分区级馆、街道馆、镇级馆、总馆、分馆和同名场馆。
- 来源标题、正文、地址、门头文字、室内标识和建筑特征应共同支持图片属于当前点位。
- 每张入选图片都需记录具体来源页、原图 URL、抓取日期、帖子或文章标题、图片序号和身份依据。一个帖子包含多个地点时逐图判断，不能整帖默认归属同一地点。
- 搜索页只写城市、行政区或简称时不能确认具体地点；外国同名场馆、邻近场馆、旧址和搬迁前图片全部排除。
- 小红书和大众点评图片需同时核对帖子标题、正文地点、地址标签、图片内门头或标识；地点标签过宽、文案混入多个场馆或无法确认分馆时排除。
- 总馆、北馆、第二图书馆、新旧馆址等易混地点，必须把正式名称和完整地址同时加入查询，并用建筑外观、门头或正文地址完成双重确认。室内风格相似不能作为身份依据。
- 证据不足时留空并记录待补。

### 人物、版权与水印

- 公开采集图片和用户提供图片均允许真实使用场景中的自然背景人物，例如多人在阅览区自习、阅读或在食堂正常用餐。人数较多，或人物较小、没有看镜头、正在进行与场所相关的自然活动时，正脸、侧脸、背影或面部可辨认都不构成淘汰理由。
- 人物判断只看构图和拍摄意图，不因图片来自公开页面而收紧。场地、空间或设施是画面主体，人物只是自然使用场景的一部分时可以保留；用户明确指定构图时，只做展示格式必需的裁切、缩放和压缩，不得自行裁掉自然人群。
- 禁止人物特写、肖像式构图、摆拍、合照、直视镜头、对镜头做动作、近距离拍摄单个用餐者，以及人物明显成为画面主体的图片。未成年人正脸被近距离清楚拍摄时也应淘汰。
- 判断重点是拍摄意图和构图：画面应在介绍场地、空间或设施，人物只是在使用场所。即使人数较多，只要读者各自自习、阅读或用餐，没有与镜头互动，且空间仍是主要信息，就可以保留。人物很小或处于远景时也允许保留。
- Apple Vision 和人脸检测只用于提示可能存在的人物，不能按人脸数量、面部是否可辨认或固定面积阈值自动淘汰。最终由 Codex 查看完整原图，判断人物是否看镜头、是否摆拍、是否为特写以及裁切后是否成为主体。
- 禁止任何水印、平台标志、账号名、版权字样、日期戳和宣传文字叠层。检查完整画面和四角，重点检查右下角。
- 小红书、大众点评等社交媒体候选图在入库前必须裁掉平台水印、账号标识和角落文字；仅允许裁切处理，裁切后仍需保留有效主体且不改变地点事实。
- 水印压在人物、设施、门头或画面主体上，或裁切会破坏构图、把背景人物放大成主体、降低地点可辨识度时，直接淘汰该图。禁止用模糊、遮盖、涂抹或生成式修补伪造干净画面。
- 优先使用授权清晰、官方公开发布或可合理用于项目展示的素材，证据档案保留出处与授权信息。

### 终审与展示

- 每张候选图必须由 Codex 查看完整原图，阅读图中文字，核对地点身份、人物、水印、重复内容和设施信息。
- Apple Vision、OCR、感知哈希、联系表和分类模型只作初筛。裁切、压缩或替换后重新查看最终文件。
- 联系表用于全局比较，不能代替逐张查看。每张入选原图和最终方图都要以可读分辨率打开；同时生成四角检查图，确认平台标识、账号名和日期戳已清除。
- 终审覆盖城市全部当前有效图片，不能只检查本轮新增文件。发现旧图低清、身份不明、裁切错误或内容价值过低时，同轮替换或移除，避免新旧标准混用。
- 逐馆检查图片组顺序：首图先回答“这是哪里”，后续图片再回答“里面有什么、使用体验怎样”。明显弱于其他候选的图片不能因已经下载或已入库而保留。
- 入库图片需存在、可访问、方向正确并符合当前方图规范；`sortOrder` 连续。
- 详情页按单张加载结果渐进显示，一张加载完成就立即显示，页面不等待整组图片完成。

## 11. 维护流程与写入安全

1. 从主库导出待处理点位 ID、正式名称、分类、地址和现有字段；新城市同时建立行政区、坐标边界和预期点位类型清单。
2. 用 Crawl4AI 多渠道发现并归档来源，建立逐字段证据清单；图片搜索至少覆盖官方与政府媒体、新闻或建筑来源、地图或旅行平台、大众点评和小红书中的可用渠道。
3. 先完成代表性样板并执行完整终审，用样板确认查询词、身份判断、简介密度、分辨率、裁切和图片排序标准，再批量运行同一套流程。
4. 审核公共服务资格、名称、机构层级和城市范围，未通过的候选停止处理。
5. 规范化地址，完成地理编码、地图交叉核验和 GCJ-02 检查。
6. 运行完全重复与近距离重复审计，处理分馆、同址机构和旧名称关系。
7. 人工整理营业时间和简介；逐点扩展图片候选，任何点位未达到第 10 节首图硬门槛时继续搜索，素材充足点位未达到数量与多样性目标时也应继续搜索。
8. 查看每张完整原图，建立入选清单；生成最终方图后，再逐张查看完整方图与四角检查图，确认身份、清晰度、人物、水印、裁切、重复和排序。
9. 批量写入前生成 SQLite 备份；脚本先预演并输出变更报告，再用事务应用。变更照片或字段后清空对应点位 `pushedFingerprint`。
10. 对变更前后记录数量、字段、坐标移动距离、照片数量和文件进行差异检查；计算非目标城市数据哈希，必须保持一致。
11. 运行第 13 节全部验证。存在未解释失败时停止发布。
12. 在后台点击“推送到小程序”，或运行 `admin/scripts/push-places-to-cloud.mjs`，只写入字段或照片发生变化以及云端缺失的地点，并清理主库已删除的云端记录。
13. 推送报告需明确“推送、跳过、清理”数量。立即再运行一次同步，预期推送 0 条；若仍有变化，查明指纹或上传路径不稳定的原因后再交付。
14. 推送后核对云端总量，逐个抽查本轮变化点位的图片数量、顺序、云端 URL、简介、地图落点和导航；提醒用户在微信开发者工具点击“编译”验证。

批量删除、合并或大范围坐标修正必须保留备份、预演报告、应用报告和证据清单。发现错误图片、错误场馆或严重定位偏差时优先从主库修正并尽快重新推送。

- 百度地图、高德地图、腾讯地图公开 POI：独立交叉核验。

- Prisma：事务写入、后台查询和数据模型维护。

- Pillow、NumPy：裁切、图像特征、pHash/dHash 和相似度初筛。
- Sharp：方图、WebP、联系表、尺寸和元数据检查。

## 13. 发布前验收

每次点位数据变更完成后逐项确认：

1. 每个新增点位符合类别、公共开放和城市范围要求。
2. 正式名称、机构层级和地址有强来源，证据可追溯。
3. 地址包含足够定位信息，坐标为 GCJ-02，门牌和地图落点一致。
4. 完全重复、60 米近距离重复及同名点位已检查，分馆关系有记录。
5. 营业时间含明确时段和当前来源；简介只含已核实实用事实。
6. 自然类图片最多 10 张，其他分类最多 5 张；无近似重复、人物特写、摆拍、合照、直视镜头和水印，正常使用场景中的自然背景人物允许保留。
7. 每个地点首图都能识别场所类别和具体地点，完整呈现场所主体；任何点位均未用石碑、局部门头、空走廊、普通书架或普通设施图充当首图；素材充足的自然点位达到 4–10 张合格图。
8. 每张图片已有来源页、原图 URL 和身份依据；完整原图、最终方图、全图联系表和四角检查表均已人工查看。
9. 本地图片存在、为方图、排序连续、无完全重复；原图清晰度和最终裁切符合第 10 节要求，详情页保持逐张加载显示。
10. 批量写入已有备份、预演报告、应用报告和差异检查；非目标城市数据哈希保持一致。
11. 运行以下命令并处理全部失败：

```bash
npm run audit:places
npm test
for f in $(find miniprogram cloudfunctions tests scripts -name '*.js' -print); do node --check "$f" || exit 1; done
```

12. 数据确认无误后增量推送到小程序，报告推送与跳过数量；第二次同步应为 0 条变化，再核对云端 `places` 数量、图片、简介、地图落点和导航。
